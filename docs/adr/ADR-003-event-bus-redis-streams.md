# ADR-003. Redis Streams как шина событий

- **Статус:** Заменено [ADR-012](ADR-012-kafka.md) (брокер – Apache Kafka)
- **Дата:** 29.09.2026
- **Автор:** Халецкий Д. Е.

## Контекст
Результаты ML (до 50 отсчетов/с при 5 встречах) должны одновременно попадать на панель организатора (≤ 2 с) и в БД,
а события жизненного цикла встреч – в несколько сервисов. Redis уже предусмотрен концепцией (кеш, очередь задач).

## Решение
Redis Streams с группами потребителей: у каждого сервиса-потребителя своя группа, т. е. поток читается независимо
(realtime – для доставки, analytics – для сохранения). ML-сервис не знает о потребителях и пользователях.

## Рассмотренные варианты
| Вариант | Плюсы | Минусы |
|---|---|---|
| **Redis Streams** | Уже в стеке, низкая задержка, группы потребителей, ACK и повторная доставка, простая эксплуатация | Ограниченная долговечность (память), нет схем «из коробки» |
| Redis Pub/Sub | Проще | Нет гарантий доставки: при рестарте analytics данные теряются |
| RabbitMQ / NATS JetStream | Богаче функции | Еще один компонент для развертывания и изучения |
| Kafka | Промышленный стандарт | Избыточно тяжело для одного VPS |
| ML → LiveKit data → организатор | Минимальная задержка | Два канала доставки, контроль доступа в ML, рассинхронизация с БД |

## Последствия
- Контракты событий – pydantic-модели в `vks_contracts`, описаны в [events.md](../api/events.md).
- Длина потоков ограничивается `MAXLEN`; Redis с AOF.
- При необходимости масштабирования можно перейти на NATS JetStream, заменив адаптер `vks_common.streams`.
