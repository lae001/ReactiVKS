# ADR-012. Apache Kafka как брокер событий

- **Статус:** Принято (заменяет [ADR-003](ADR-003-event-bus-redis-streams.md))
- **Дата:** 29.09.2026
- **Автор:** Халецкий Д. Е.

## Контекст
Требования к шине не изменились: результаты ML (до ≈ 250 сообщений/с при 5 встречах × 10 участников × 5 кадров/с)
должны одновременно попадать на панель организатора (≤ 2 с) и в БД; события жизненного цикла встреч, согласий и
пользователей – в несколько сервисов. Команда решила использовать в качестве брокера Apache Kafka вместо
Redis Streams: промышленный стандарт для событийно-ориентированных микросервисов, долговременное хранение журнала,
повторное чтение с любого смещения, практический опыт работы с Kafka для команды.

## Решение
- Apache Kafka 3.9 (или 4.x) в режиме **KRaft** (без ZooKeeper), **один брокер** на демонстрационном сервере,
  коэффициент репликации 1.
- Топики по доменам с ключом упорядочивания `meeting_id` / `user_id`; перечень, партиции и хранение – [events.md](../api/events.md).
- Клиент – `aiokafka` (asyncio) в сервисах и ML-сервисе, обертка в `vks_common.kafka`.
- Сообщение: ключ + JSON-конверт + заголовки; Schema Registry не используется, совместимость контрактов проверяется в CI
  по JSON Schema из `vks_contracts`.
- Сервисы с БД публикуют через transactional outbox ([ADR-011](ADR-011-transactional-outbox.md)).
- Redis остается в Системе, но **не как брокер**: кеш прав доступа, ограничение частоты запросов, ключи идемпотентности,
  распределенные блокировки фоновых задач.

## Рассмотренные варианты
| Вариант | Плюсы | Минусы |
|---|---|---|
| Redis Streams (ADR-003) | Уже в стеке, легкий | Хранение в памяти, слабее инструменты, менее распространен как брокер |
| **Apache Kafka (KRaft)** | Долговременный журнал, повторное чтение, группы потребителей, упорядочивание по ключу, зрелая экосистема и мониторинг, отраслевой стандарт | Тяжелее в эксплуатации (≈ 1–1,5 ГБ ОЗУ), на одном брокере нет отказоустойчивости, нет встроенной отложенной повторной доставки |
| Redpanda | Совместим с API Kafka, легче | Лицензия BSL, меньше учебных материалов |
| RabbitMQ / NATS JetStream | Проще эксплуатация | Не соответствует выбору команды |

## Последствия
- В compose добавляются `kafka` и однократный `kafka-init` (создание топиков); в профиле `monitoring` – `kafka-exporter`,
  в профиле `dev` – веб-интерфейс `kafka-ui`.
- Ресурсы: брокер – 1 CPU, 1,5 ГБ ОЗУ (heap 768 МБ), диск – единицы ГБ (хранение 1 ч – 14 сут). Бюджет сервера
  16 ГБ сохраняется (Redis уменьшен до 256 МБ).
- Повторная доставка при ошибке обработки реализуется в потребителе (повторы в процессе + топик `<topic>.dlq`),
  так как в Kafka нет аналога списка ожидания Redis (PEL) – см. [conventions.md](../backend/conventions.md#7-потребление-событий).
- Фиксация смещений в analytics-service согласуется с записью посекундных корзин (коммит только до первого
  несохраненного сообщения в партиции).
- realtime-service использует группу на экземпляр – каждой реплике нужны все события.
- Один брокер – единая точка отказа плоскости анализа; видеосвязь от него не зависит. Для продуктивной эксплуатации –
  кластер из 3 брокеров с `replication.factor=3`, `min.insync.replicas=2` (изменение только конфигурации).
- Интеграционные тесты – testcontainers с образом `apache/kafka`.
