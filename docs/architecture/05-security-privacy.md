# 5. Безопасность и защита персональных данных

## 5.1 Модель угроз (кратко)

| Угроза | Мера |
|---|---|
| Перехват трафика | HTTPS/WSS (TLS 1.2+, HSTS) на Nginx; медиа – DTLS-SRTP (обязательно в WebRTC); TURN/TLS |
| Подбор пароля | Argon2id; ограничение частоты `/auth/login` (5 попыток / 15 мин на IP + e-mail) в Redis и `limit_req` в Nginx |
| Кража access-токена (XSS) | Токен только в памяти SPA, срок 15 мин; строгий CSP; React экранирует вывод; нет `dangerouslySetInnerHTML` |
| Кража refresh-токена | Cookie `httpOnly; Secure; SameSite=Strict; Path=/api/v1/auth`; ротация с обнаружением повторного использования |
| CSRF | Refresh-cookie `SameSite=Strict`; остальные запросы – заголовок `Authorization`, cookie не используются |
| Подбор ссылки на встречу | `invite_code` – 10 символов base32 (≈ 50 бит); ограничение частоты `/join/*` |
| Участник подделывает согласие или роль | Атрибуты `vks.*` выставляет только meeting-service; в токене LiveKit `canUpdateOwnMetadata = false` |
| Участник видит чужие результаты | Результаты доступны только через realtime/analytics с проверкой `owner_id`; ML не отправляет данные в комнату |
| Доступ к внутренним API извне | `/internal/*` не проксируются Nginx; сервисы в отдельной Docker-сети; заголовок `X-Service-Token` |
| Подделка или чтение событий в брокере | Порт Kafka не публикуется наружу; SASL/SCRAM + ACL на топики для каждого сервиса |
| Утечка кадров | Кадры только в оперативной памяти ML-сервиса; запрет отладочного сохранения в production (проверка при старте) |
| Подделка вебхуков LiveKit | Проверка подписи (JWT в заголовке `Authorization`, SHA-256 тела) ключом API LiveKit |

## 5.2 Аутентификация

### Пользователи (организатор, администратор)

- auth-service выпускает **access-токен JWT RS256** (15 мин) и **refresh-токен** (случайные 256 бит, 30 дней, в БД – SHA-256).
- Claims access-токена: `iss=vks-auth`, `aud=vks`, `sub` (user_id), `role` (`organizer` | `admin`), `name`, `iat`, `exp`, `jti`.
- Публичный ключ публикуется в `GET /api/v1/auth/.well-known/jwks.json`; остальные сервисы загружают JWKS при старте
  и кешируют (обновление раз в час / при неизвестном `kid`). Проверка токена выполняется локально в каждом сервисе
  общей библиотекой `vks_common.auth` ([ADR-005](../adr/ADR-005-gateway-and-jwt.md)).
- Блокировка пользователя отзывает refresh-токены и публикует `user.blocked`; уже выданный access-токен действует
  не дольше 15 мин. meeting-service дополнительно отклоняет вход во встречу заблокированного организатора
  (проекция `meeting.blocked_users` из `user.events`).

### Участники-гости

- При входе по ссылке meeting-service выдает:
  - `participant_token` – случайные 256 бит (в БД – хеш), действует до конца встречи; используется для
    `PUT /participants/me/consent` и `POST /participants/me/leave`;
  - `livekit_token` – JWT LiveKit (HS256, ключ API LiveKit), срок 6 ч, с grants (см. ниже).

### Сервисы

- Межсервисные вызовы `/internal/*`: заголовок `X-Service-Token` (секрет из переменной окружения, свой для каждой пары
  не требуется в MVP – один общий секрет внутренней сети).
- ML-сервис → LiveKit: ключ API LiveKit (протокол LiveKit Agents).
- Сервисы → Kafka: SASL/SCRAM-SHA-512, отдельный пользователь на сервис; ACL Kafka – запись только в свои топики
  (`auth` → `user.events`; `meeting` → `meeting.events`; `analytics` → `report.events`; `ml` → `emotion.samples`,
  `ml.status`; каждому потребителю – `*.dlq` своих входных топиков), чтение – только нужных топиков и своих групп.
  Внутри Docker-сети – `SASL_PLAINTEXT` (сеть недоступна извне, порт Kafka не публикуется); в dev-окружении
  аутентификация отключена.
- Сервисы → Redis: пароль (`requirepass`).
- Сервисы → PostgreSQL: отдельный пользователь на схему.

## 5.3 Авторизация

| Ресурс | Правило |
|---|---|
| Встреча (чтение, изменение, завершение, модерация) | `meetings.owner_id = sub` |
| Панель эмоций (WebSocket-подписка) | `owner_id = sub` (проверка через `/internal/meetings/{id}/access`) |
| Отчет, ряды, экспорт, отметки | `meeting_projection.owner_id = sub` |
| Согласие | Только сам участник (`participant_token`) |
| Администрирование | `role = admin` |

Администратор **не** получает доступ к отчетам организаторов через API (минимизация доступа к ПДн).

### Права в токене LiveKit

| Grant | Организатор | Гость | emotion-agent |
|---|---|---|---|
| `roomJoin` | ✓ | ✓ | ✓ |
| `canPublish` | ✓ | ✓ | ✗ |
| `canSubscribe` | ✓ | ✓ | ✓ |
| `canPublishData` | ✓ (чат) | ✓ (чат) | ✗ |
| `canUpdateOwnMetadata` | ✗ | ✗ | ✗ |
| `hidden` | ✗ | ✗ | ✗ (агент должен быть виден клиентам, чтобы показывать индикатор анализа; интерфейс не рисует для него плитку) |
| `roomAdmin` | ✗ (модерация через meeting-service) | ✗ | ✗ |

## 5.4 Защита персональных данных (152-ФЗ)

Изображение лица – персональные данные; при использовании для установления личности – биометрические (ст. 11).
Система **не устанавливает личность** по изображению (нет распознавания лиц, сравнения с эталонами), а связывает
результат с участником по его видеодорожке. Тем не менее Система реализует меры как для ПДн повышенной чувствительности:

| Принцип | Реализация |
|---|---|
| Согласие | Явный выбор перед входом во встречу с анализом; текст уведомления версионируется (`notice_version`); журнал решений `consents` |
| Информирование | Индикатор «Идет анализ эмоций» у всех участников, пока в комнате присутствует `emotion-agent`, и собственный статус согласия у каждого участника |
| Отзыв согласия | Кнопка в интерфейсе встречи; прекращение анализа в течение ≤ 1 с |
| Минимизация | Кадры не сохраняются; хранятся только посекундные вероятности; нет эмбеддингов лиц |
| Ограничение доступа | Результаты – только организатору встречи |
| Удаление | Организатор удаляет встречу → физическое удаление аналитики; автоматическая очистка по сроку хранения |
| Локализация | Все компоненты и данные – на сервере в РФ; нет внешних облачных API |
| Вероятностный характер | Предупреждение в панели, отчете и PDF: «Результаты отражают внешнее выражение лица и носят рекомендательный характер» |

Текст уведомления и согласия хранится в репозитории (`frontend/src/shared/legal/consent-notice.v1.md`) и
согласуется с заказчиком. Изменение текста – новая версия.

## 5.5 Заголовки и настройки Nginx

- `Strict-Transport-Security: max-age=31536000`
- `Content-Security-Policy: default-src 'self'; connect-src 'self' wss://livekit.<домен>; media-src 'self' blob:; img-src 'self' data: blob:; frame-ancestors 'none'`
- `Permissions-Policy: camera=(self), microphone=(self), display-capture=(self)`
- `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer` (не передавать `invite_code` сторонним сайтам)
- `limit_req` для `/api/v1/auth/*` и `/api/v1/join/*`.

## 5.6 Журналирование

- Структурированные JSON-журналы (`structlog`), обязательные поля: `service`, `level`, `request_id`, `meeting_id`.
- Запрещено журналировать: пароли, токены, `invite_code` целиком, изображения, вероятности эмоций конкретного участника
  с его именем (в журналах – только `participant_id`).
