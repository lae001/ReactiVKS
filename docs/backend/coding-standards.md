# Стандарты кодирования бэкенда

Обязательны для всех Python-сервисов в `backend/` (auth-, meeting-, realtime-, analytics-service) и общих библиотек.
Расхождение кода с этим документом – дефект того же веса, что упавший тест. Документ самодостаточен: правила
устройства сервиса, именования, тестов и git описаны здесь целиком.

Связанные документы: механизмы общей библиотеки – [conventions.md](conventions.md), физическая схема БД –
[database.md](database.md), контракты – [../api/](../api/), инструменты и CI –
[../architecture/07-development.md](../architecture/07-development.md).

**Язык.** Идентификаторы – на английском; комментарии, docstring, сообщения коммитов и документация – на русском
(требование концепции, п. 8.5). Сообщения журналов (`_logger.info("user registered")`) и `detail` ошибок API – на
английском: журналы ищутся по стабильным строкам, а текст для пользователя фронтенд берет по `code`.

---

## 1. Базовые принципы

1. **Инвариант защищается там, где его нельзя обойти.** Уникальность e-mail – ограничение PostgreSQL, а не проверка
   в коде. Правило, которое держится на дисциплине разработчика, однажды будет нарушено новым путем записи.
2. **Правило, которое не проверяется автоматически, не существует.** Каждое ограничение этого документа проверяется
   линтером, типами, тестом или CI либо стоит в чек-листе ревью (§15). Все остальное – пожелание.
3. **Границы важнее внутренностей.** Внутри модуля допустим любой разумный стиль. На границе слоя, сервиса или
   события – только то, что написано здесь.
4. **Согласованность важнее личного вкуса.** Новый код пишется в стиле окружающего. Стиль меняется отдельным
   изменением, а не попутно.
5. **Явное лучше умного.** Метапрограммирование, динамическая генерация классов, неявные регистрации по импорту
   запрещены. Читатель должен видеть, что происходит, не запуская код.
6. **Если правило мешает – меняется правило, а не обходится молча.** Обоснованное отступление оформляется ADR и
   правкой этого документа в том же pull request.
7. **Учебная цель не отменяет инженерную дисциплину.** Код доводится до рабочего состояния, а не до демонстрации.
   `TODO` без ключа задачи (`EMO-N`) не переживает ревью.

## 2. Структура

### 2.1 Репозиторий бэкенда

```text
backend/
├── pyproject.toml           # корень uv workspace: dev-зависимости, ruff, mypy, pytest, import-linter
├── uv.lock  Makefile  .python-version
├── libs/
│   ├── vks_common/src/vks_common/       # шасси: см. §2.3
│   └── vks_contracts/src/vks_contracts/ # модели событий и внутренних API (появляется с первым событием)
└── services/
    ├── auth_service/src/auth_service/
    ├── meeting_service/src/meeting_service/
    ├── realtime_service/src/realtime_service/
    └── analytics_service/src/analytics_service/
```

Пакет каждого сервиса называется уникально (`auth_service`, не `app`): в uv workspace все пакеты ставятся в одно
окружение, и одинаковые имена конфликтуют.

### 2.2 Устройство сервиса

```text
services/auth_service/
├── pyproject.toml  Dockerfile  alembic.ini
├── migrations/versions/        # схема БД – только здесь
├── src/auth_service/
│   ├── main.py                 # create_application(): сборка, роутеры, lifespan
│   ├── settings.py             # наследник BaseServiceSettings
│   ├── cli.py                  # ── вход: командная строка (vks-auth create-admin)
│   ├── api/v1/                 # ── вход: HTTP (роутеры и сборка зависимостей)
│   ├── schemas/                # ── DTO запросов и ответов (pydantic)
│   ├── consumers/              # ── вход: Kafka
│   ├── workers/                # ── вход: время (периодические задачи)
│   ├── services/               # ── сценарии: границы транзакций
│   ├── domain/                 # ── правила и порты (Protocol): без ввода-вывода
│   ├── repositories/           # ── доступ к данным: весь SQL
│   ├── models/                 # ── ORM: отображение таблиц
│   ├── adapters/               # ── реализации портов домена: криптография, Redis, LiveKit, SMTP
│   └── clients/                # ── исходящие вызовы других сервисов (/internal/*)
└── tests/{unit,integration,api}/
```

Каталоги, которые сервису не нужны, не создаются пустыми.

| Слой | Отвечает за | Не делает |
|---|---|---|
| `api`, `cli`, `consumers`, `workers` | Разбор входа → вызов сценария → формирование ответа | Бизнес-логику, SQL, транзакции |
| `schemas` | Форма запроса и ответа, валидация формата | Бизнес-правила |
| `services` | Один сценарий использования, границы транзакции, порядок вызовов | HTTP (статусы, `Request`), SQL |
| `domain` | Сущности, value-объекты, правила, доменные ошибки, порты (`Protocol`) | Ввод-вывод, `now()`, генерацию UUID |
| `repositories` | SQL и преобразование ORM ↔ доменная сущность | Коммит, бизнес-решения |
| `models` | Декларативные классы SQLAlchemy | Логику |
| `adapters` | Реализацию порта домена над внешней библиотекой или системой | Решения, которые принадлежат домену |
| `clients` | HTTP-вызовы других сервисов с таймаутами и повторами | Бизнес-логику |

### 2.3 Правила импорта между слоями

| Слой | Может импортировать | Не может |
|---|---|---|
| `domain` | стандартную библиотеку, `domain`, **только** `vks_common.errors` (базовые классы ошибок) | всё остальное, включая pydantic и SQLAlchemy |
| `models` | SQLAlchemy, `vks_common.db` | всё остальное своего сервиса |
| `repositories` | `domain`, `models`, `vks_common.db` | `services`, `api`, `clients`, `adapters` |
| `adapters` | `domain`, `settings`, внешние библиотеки, `vks_common` | `services`, `api`, `repositories`, `models` |
| `clients` | `domain`, `vks_common`, `vks_contracts` | `services`, `api`, `repositories`, `models` |
| `services` | `domain`, `repositories`, `clients`, `vks_common`, `vks_contracts` | `api`, `cli`, `consumers`, `workers`, `adapters`, `models` |
| `api`, `cli`, `consumers`, `workers` | `services`, `schemas`, `domain`, `vks_common` | `repositories`, `models`, `clients` |
| `main.py` | всё (корень сборки: создает адаптеры и передает их в сценарии) | – |

Сценарий получает адаптер через конструктор, типизированный портом из `domain` (`PasswordHasher`, `TokenSigner`),
поэтому `services` не импортирует `adapters`: конкретную реализацию выбирает `main.py`, в тестах – фикстура.

Правила проверяются `import-linter` (контракты – в `backend/pyproject.toml`) в CI и pre-commit.

**Категорически запрещено:** импорт из `services/<другой>/`. Между сервисами существуют только события Kafka и
HTTP-контракты; общие типы живут в `vks_contracts`.

### 2.4 Что попадает в шасси

`vks_common` – инфраструктура, общая минимум для двух сервисов и **не содержащая доменной логики**: конфигурация,
журналы, ошибки, фабрика приложения, БД, проверка JWT, часы и идентификаторы, затем Kafka, outbox, фоновые задачи,
HTTP-клиент ([conventions.md](conventions.md#1-библиотека-vks_common)). Модуль появляется в шасси вместе с первым
сервисом, которому он нужен, а не заранее.

Доменные типы в шасси запрещены: они привязывают релизный цикл всех сервисов к одному пакету. Модуль `utils.py` не
создается никогда: функция кладется туда, где применяется по смыслу.

## 3. Именование

| Сущность | Правило | Пример |
|---|---|---|
| Модули и пакеты | `snake_case`, существительное | `refresh_tokens.py` |
| Классы | `PascalCase` | `RefreshTokenRepository` |
| Сценарии | Глагол + объект | `RegisterUser`, `RefreshSession` |
| Функции и переменные | `snake_case` | `build_access_claims` |
| Константы | `UPPER_SNAKE` | `REFRESH_TOKEN_TTL_DAYS` |
| Булевы | префикс `is_`, `has_`, `can_` | `is_blocked`, `can_sign_in` |
| Асинхронные функции | без суффикса `_async` | `async def get_by_email` |
| Таблицы БД | `snake_case`, множественное число | `refresh_tokens` |
| Колонки времени | суффикс `_at` (момент), `_on` (дата) | `created_at`, `last_login_at` |
| Ограничения БД | `<таблица>_<поле>_ck` / `_uk` / `_idx`, FK – `<таблица>_<поле>_fkey` ([database.md](database.md#общие-правила)) | `users_email_uk` |
| Топики Kafka | по [events.md](../api/events.md#топики) | `user.events` |
| Типы событий | `<агрегат>.<прошедшее время>` | `user.blocked` |
| Классы событий | `PascalCase` от типа | `UserBlocked` |
| Метрики | `<subject>_<unit>_total` / `_seconds` | `logins_total` |
| Фикстуры pytest | существительное без `test_` | `user_factory` |
| Ветки git | §15 | `feat/EMO-33-auth-service` |

**Доменный словарь** – по глоссарию концепции: организатор – `organizer`, гость – `guest`, участник – `participant`,
встреча – `meeting`, согласие – `consent`. Синонимы (`host`, `attendee`, `room` для встречи) не используются;
`room` – только комната LiveKit.

**Запрещенные имена** модулей и классов внутри сервиса: `data`, `info`, `obj`, `manager`, `helper`, `utils`,
`common`. Имя должно называть предмет.

## 4. Типизация и форматирование

- Форматирование – `ruff format`, длина строки – 120 символов (как перенос текста в `docs/`).
- `mypy --strict` без исключений по модулям. Послабления – только для `migrations/` и `tests/`, и они прописаны
  в `pyproject.toml`.
- `Any` запрещен (ruff `ANN401`). Неизвестный тип – `object` с явным сужением.
- `# type: ignore` – только с кодом ошибки и причиной: `# type: ignore[arg-type]  # у aiokafka нет заглушек`.
- Публичные функции аннотируются полностью, включая `-> None`.
- Порты домена – `typing.Protocol`, не абстрактные классы: домен не наследуется от инфраструктуры даже формально.
- Идентификаторы – `NewType`, а не голый `UUID`: `UserId = NewType("UserId", UUID)`. Перепутанные местами
  идентификаторы – частая ошибка системы, где всё является UUID, и типы ловят ее бесплатно.
- Время – только `datetime` с зоной (UTC); наивный `datetime` запрещен (ruff `DTZ`).

## 5. Модели данных: три раздельных представления

| Вид | Где | Чем является |
|---|---|---|
| Схема API | `schemas/` | pydantic-модель запроса или ответа |
| Доменная сущность | `domain/` | `@dataclass(frozen=True, slots=True)` без зависимостей |
| ORM-модель | `models/` | декларативный класс SQLAlchemy |

Представления не смешиваются. Репозиторий возвращает доменную сущность; преобразование ORM → домен – явная функция
рядом с репозиторием. Возвращать ORM-модель из сценария или роутера запрещено: это привязывает контракт API к схеме
БД, и любая миграция становится ломающим изменением API. Роутер строит ответ из того, что вернул сценарий.

Доменная сущность неизменяема. Изменение состояния возвращает новый объект (`dataclasses.replace`).

## 6. Домен

- Никаких обращений к БД, сети, Redis, `datetime.now()` и генерации UUID внутри домена: время и идентификаторы
  передаются аргументами. Иначе домен не тестируется детерминированно.
- Бизнес-правила – методы сущности или чистые функции модуля, а не код сценария. Правило, написанное в `services/`,
  не покрыто быстрыми тестами и дублируется при втором способе вызова.
- Доменные ошибки наследуются от классов `vks_common.errors` (`Conflict`, `Unauthorized`, …) и несут `code` из
  [реестра](../api/rest-api.md#реестр-кодов-ошибок). Это единственный импорт шасси, разрешенный домену.

```python
class EmailTaken(Conflict):
    """Адрес уже занят другой учетной записью."""

    code = "email_taken"
    title = "Email is already registered"
```

- Валидация значений – в конструкторах value-объектов и чистых функциях домена, а не в сценариях.
- Порты (`PasswordHasher`, `TokenSigner`, `LiveKitGateway`) объявляются в домене; реализации – в `adapters/`.
- Домен не знает о существовании других сервисов: данные другого сервиса – это входные данные, а не зависимость.

## 7. Сценарии (`services/`)

- Один сценарий – один класс с единственным публичным методом `execute`. `UserService` с восемью методами – не
  сценарий, а god-object.
- Транзакция начинается и заканчивается **в сценарии** (`async with transaction(session)`), не в репозитории и не
  в роутере. Репозиторий никогда не коммитит: иначе изменение и запись в `outbox` невозможно объединить.
- В одной транзакции с изменением состояния пишется событие в `outbox`; публикация в Kafka напрямую из сценария
  запрещена ([ADR-011](../adr/ADR-011-transactional-outbox.md)).
- **Сетевые вызовы и тяжелые вычисления – вне транзакции.** Вызов другого сервиса, LiveKit или хеширование пароля
  (Argon2 занимает CPU на десятки миллисекунд) выполняются до `BEGIN` или после `COMMIT`; держать соединение с БД
  на время такой работы запрещено. CPU-тяжелая работа уходит в поток (`asyncio.to_thread`).
- Сценарий не знает о HTTP: не принимает `Request`, не возвращает `Response`, не оперирует статус-кодами. Он
  возбуждает доменную ошибку, а обработчик шасси превращает ее в Problem Details.
- Зависимости передаются через конструктор; время – через `Clock` из `vks_common.clock`. Сценарий собирается в тесте
  без поднятия приложения.
- Один сценарий вызывается и из роутера, и из CLI, и из потребителя. Если для второго входа нужна «почти такая же»
  логика – сценарий разбит неправильно.

## 8. Работа с БД

- Только асинхронный SQLAlchemy 2.x, стиль `select()`; `session.query()` запрещен.
- Ленивая загрузка отключена (`lazy="raise"`), связи загружаются явно (`selectinload`).
- **Область видимости обязательна в каждом запросе списка.** Выборка фильтруется по владельцу в самом SQL
  (`WHERE owner_id = :sub`), а не в Python после выборки: фильтрация после выборки ломает пагинацию. Метод
  репозитория, который принимает только фильтры без контекста доступа, – повод для отказа на ревью.
- Сырой SQL допустим там, где ORM мешает; он оформляется отдельной функцией с комментарием, зачем понадобился, и
  покрывается интеграционным тестом.
- SQLSTATE различается явно: `23505` (`unique_violation`) по имени ограничения – это `email_taken`; ловить
  `IntegrityError` целиком и трактовать как один конкретный конфликт – дефект.
- Любой внешний вызов (HTTP, Redis, Kafka, LiveKit, SMTP) имеет таймаут. Вызов без таймаута – дефект.
- Синхронный вызов другого сервиса – только из `clients/`, с параметрами из
  [conventions.md](conventions.md#5-межсервисные-вызовы).

### Миграции

- Только Alembic; `alembic_version` – в схеме сервиса (`version_table_schema`). `Base.metadata.create_all` не
  используется нигде, включая тесты: тесты гоняют реальные миграции.
- Одна миграция – одно логическое изменение, с осмысленным именем файла (`0001_users_and_refresh_tokens.py`).
- `downgrade` обязателен, кроме миграций данных, где он невозможен (тогда – комментарий с причиной).
- Политика **expand/contract**: сначала добавить, перевести код, потом удалить. Переименование колонки одним шагом
  запрещено.
- Имена ограничений задаются явно и следуют [database.md](database.md#общие-правила); при изменении схемы
  database.md обновляется в том же pull request.
- Таблица создается миграцией той задачи, которая ее использует, а не заранее.

## 9. API

Контракт – [rest-api.md](../api/rest-api.md); расхождение кода и документа исправляется в том же pull request.

- Пути – существительные во множественном числе, `kebab-case`, версия в пути: `/api/v1/users/me/password`.
- Коды ответов и ошибок – только из реестра контракта. Ошибки – `application/problem+json` с полями `type`,
  `title`, `status`, `detail`, `code`, `request_id`; у `validation_error` – еще `errors[]`.
- Чужой ресурс – `404`, а не `403`: ответ не раскрывает существование ресурса.
- Списки – только курсорная пагинация `{"items": [...], "next_cursor": …}`; `offset` запрещен.
- Ответ никогда не содержит ORM-полей, хешей, внутренних флагов и идентификаторов чужих сервисов.
- Время в API – ISO 8601 в UTC.
- Каждый эндпоинт явно объявляет доступ: `require_user`, `require_admin`, `require_service` или явное «все» в
  документации контракта. Эндпоинт без проверки – незакрытая задача.

## 10. События

- Тип – факт в прошедшем времени: `user.blocked`, `meeting.ended`. Команд в шине нет.
- Конверт и обязательные поля – по [events.md](../api/events.md); схема события – pydantic-модель в
  `vks_contracts`, один источник правды для производителя и потребителя.
- Потребитель – tolerant reader: неизвестные поля игнорируются, незнакомый `type` журналируется и пропускается.
- Обработчик события идемпотентен всегда ([conventions.md](conventions.md#7-потребление-событий)).
- Событие несет данные своего агрегата, достаточные для реакции, а не ссылку «сходи и получи».
- Ключ сообщения – идентификатор агрегата (`user_id`, `meeting_id`).

## 11. Ошибки, журналы, телеметрия

- `except Exception` без повторного возбуждения запрещен; пустой `except: pass` запрещен без исключений.
- Журналы структурные, только через `vks_common.logging.get_logger`; `print` запрещен (ruff `T20`).
- **Никогда не журналируются:** пароли и их хеши, access- и refresh-токены, заголовок `Authorization`, cookie,
  закрытые ключи, `participant_token`, `invite_code` целиком, e-mail и имена (только `user_id` /
  `participant_id`), вероятности эмоций участника вместе с его именем
  ([05-security-privacy.md](../architecture/05-security-privacy.md#56-журналирование)).
- Уровни: `error` – требует вмешательства человека; `warning` – аномалия, с которой система справилась (повтор,
  обнаружено повторное использование токена); `info` – значимое бизнес-событие; `debug` – только dev. Ожидаемая
  ошибка клиента (`4xx`) – не `error`.
- `request_id` попадает в каждую запись запроса автоматически через `contextvars`; вручную не прокидывается.
- Метрика заводится вместе с ответом на вопрос «какое решение я приму, увидев ее изменение». Идентификаторы
  (`user_id`, `meeting_id`, конкретный URL) в лейблах запрещены.

## 12. Конфигурация и секреты

- Только переменные окружения через `pydantic-settings` (наследник `BaseServiceSettings`); чтение `os.environ`
  напрямую запрещено вне шасси.
- Валидация при старте, падение при неполной конфигурации.
- Значения по умолчанию допустимы для локальной разработки, но не для секретов. Для `ENV=production` проверяются
  опасные значения (например, refresh-cookie без `Secure`).
- Секретные поля – `SecretStr`; секрет можно передать файлом через переменную `<ИМЯ>_FILE` (Docker secrets).
- В git – только `.env.example`. Закрытые ключи в репозиторий не попадают никогда (pre-commit `detect-private-key`).
- Сервис при старте сверяет версию схемы БД с головой миграций и падает при расхождении.
- Каждая переменная окружения описана в документации сервиса.

## 13. Асинхронность и фоновые задачи

- Весь ввод-вывод асинхронный. Блокирующий или CPU-тяжелый вызов в корутине – дефект; выносится в
  `asyncio.to_thread` с комментарием, зачем.
- `asyncio.create_task` без сохранения ссылки и обработки исключения запрещен; фоновые задачи запускаются через
  `lifespan` шасси.
- Фоновая задача перезапускаема: прерывание в любой момент не оставляет систему в противоречивом состоянии.
- Защита от параллельного выполнения на нескольких репликах – по [background-jobs.md](background-jobs.md).
- Завершение по `SIGTERM`: дренирование запросов, остановка потребителей с коммитом смещений, закрытие пулов.

## 14. Тесты

- Структура теста – **Arrange → Act → Assert**, блоки разделены пустой строкой.
- Имя описывает поведение: `test_login_returns_403_when_user_is_blocked`.
- Один тест – одно поведение; несколько `assert` допустимы, если описывают одно поведение.
- **Собственный код не мокается.** Подменяются только внешние границы (SMTP, LiveKit); PostgreSQL, Redis и Kafka
  поднимаются в testcontainers.
- Домен тестируется без инфраструктуры. Если для теста правила нужна БД – правило лежит не в том слое.
- Каталоги: `tests/unit` (домен, адаптеры без сети – миллисекунды), `tests/integration` (репозитории, миграции,
  сценарии с БД), `tests/api` (эндпоинты через `httpx.AsyncClient` поверх ASGI).
- Обязательные тесты каждого эндпоинта: без аутентификации, с недостаточной ролью, доступ к чужому ресурсу,
  невалидный ввод.
- Фикстуры – фабрики: тест задает значимые для него поля, остальное фабрика заполняет по умолчанию.
- `time.sleep` запрещен; время подменяется фиксированным `Clock`, ожидание – опросом условия с таймаутом.
- Контейнеры поднимаются один раз на сессию pytest; изоляция тестов – откатом транзакции (сессии теста работают в
  точках сохранения внутри внешней транзакции). Тесты гонок, которым нужны настоящие параллельные транзакции,
  чистят свои строки сами.
- Флейки чинятся или удаляются; `@pytest.mark.skip` без ключа задачи запрещен.
- Порог покрытия – 60 % на сервис, цель для `domain/` и `services/` – 80 %.

## 15. Git и ревью

- **GitHub Flow**: `main` всегда рабочая, ветка на задачу от `main`, слияние только через pull request с зеленым CI
  и одобрением архитектора.
- Имя ветки: `<тип>/EMO-<N>-<slug>` – `feat/EMO-33-auth-service`, `fix/EMO-70-…`, `docs/…`, `ci/…`.
- Зависимые задачи допускается вести **стеком**: следующая ветка ответвляется от предыдущей, pull request
  открывается в предыдущую ветку и перенацеливается на `main` после ее слияния.
- Коммиты – **Conventional Commits на русском**, область – сервис или часть (`auth`, `common`, `deploy`, `ci`,
  `backend`, `api`), в конце – ключ задачи. В теле – «почему», а не «что»:

```text
feat(auth): ротация refresh-токенов с обнаружением повторного использования (EMO-33)

Повторно предъявленный токен отзывает всю семью: разлогинивается только
скомпрометированное устройство, остальные сессии пользователя живут.
```

- Коммиты атомарные: каждый – логически цельный шаг, после которого проверки зеленые. Без «wip» и «fix review».
- Один pull request – одна задача плана; больше ~400 строк кода (без тестов и документации) – повод разбить.
- Внутри ветки история линейная (`rebase`), без merge-коммитов.
- Изменение контракта (`docs/api/*`, `vks_contracts`) – в том же pull request, что и код, с ревью стороны-потребителя.

### Чек-лист ревью

1. Слои не нарушены, чужой сервис не импортирован (`import-linter` зеленый).
2. Область видимости по владельцу – в SQL всех запросов списков.
3. Событие пишется в outbox в той же транзакции, что и изменение состояния.
4. Обработчик события идемпотентен, коммит смещения – после коммита транзакции.
5. Внешние вызовы имеют таймаут; сетевые вызовы и хеширование – вне транзакции БД.
6. Ошибки – Problem Details с кодом из реестра контракта.
7. В журналах нет чувствительных данных; уровни расставлены верно.
8. Тесты задачи написаны, включая отказ в доступе и невалидный ввод.
9. Миграция обратима, следует expand/contract, database.md обновлен.
10. Документация и ADR обновлены, если решение изменилось.

## 16. Запрещенные практики

| Запрещено | Причина |
|---|---|
| Импорт между сервисами | Распределенный монолит |
| Доменные типы в шасси | Общий релизный цикл всех сервисов |
| Публикация в Kafka вне outbox (для сервисов с БД) | Потеря атомарности ([ADR-011](../adr/ADR-011-transactional-outbox.md)) |
| Сетевой вызов или хеширование пароля внутри открытой транзакции | Удержание соединения, исчерпание пула |
| HTTP-вызов другого сервиса не из `clients/` | Нет таймаута и повторов |
| Бизнес-логика в роутере | Невозможность тестировать без HTTP |
| ORM-модель в ответе API или в сценарии | Контракт привязан к схеме БД |
| Коммит внутри репозитория | Невозможно объединить изменение и outbox |
| Ловля `IntegrityError` целиком как одного конфликта | Маскирует другие нарушения |
| Наивный `datetime` | Неоднозначный момент времени |
| `offset`-пагинация | Пропуски и повторы при конкурентных вставках |
| Мок собственного репозитория в интеграционном тесте | Тест проверяет мок, а не систему |
| `Base.metadata.create_all` где угодно | Миграции остаются непроверенными |
| Ленивая загрузка связей | Незаметный N+1 |
| Идентификатор в лейбле метрики | Взрыв кардинальности |
| Глобальное изменяемое состояние, синглтоны на уровне модуля | Невоспроизводимые тесты; состояние живет в `app.state` |
| Модуль `utils.py` | Свалка без владельца |
| `TODO` без ключа задачи | Вечный долг |
| `print` | Неструктурированный вывод мимо журналов |

## Приложение. Чем проверяется каждое правило

| Раздел | Инструмент |
|---|---|
| §2.3 импорты между слоями, изоляция сервисов | `import-linter` (CI, pre-commit) |
| §3 именование, §4 типизация | `ruff` (`N`, `UP`, `DTZ`, `S`, `ASYNC`, `ANN401`, `T20`), `mypy --strict` |
